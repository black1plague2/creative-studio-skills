# What was actually validated

Date: 13 October 2026. This record covers repository construction, the original examples, and local checks. It does not promise identical performance across every AI host/model.

## Library and publication contents

- Fifteen task-specific SKILL.md folders, local production/intake/quality/example references, and the skills index were inspected.
- All fifteen passed the skill-creator metadata/frontmatter validator during construction.
- Repository validation checks metadata, local Markdown/HTML references, selected host-path/credential-like patterns, and index consistency.
- The research registry contains 58 distinct repository entries with inspection depth and limitations.
- Original user reference decks/video, font binaries, model weights, voice recordings, credentials and local host paths are not included as publication assets.

## GPT poster example

- Three original CampusCart posters were generated using the built-in GPT image tool. Cover used as style/character reference for the problem and workflow images.
- Actual images were inspected for key exact copy, stage order, same-camera continuity, palette, hierarchy and fictional-concept status.
- Native images are 1672×941, rounded within half a pixel of 16:9. They were not stretched, cropped or painted over. Exact 1920×1080 PNG output is not claimed.
- PDF and PPTX use exact 16:9 containers with three pages/slides in manifest order.
- PDF was reopened and all three Poppler-rendered pages inspected visually.
- PPTX ZIP/XML was checked for exact slide geometry, three slides, one visible image per slide and no duplicated native visible text. The example PPTX was not visually inspected in PowerPoint during this publication phase.
- Copy/transcript and packaging records are included. The packaging report records inputs/order/generated names; separate checks established final-file properties.

## Script tests

Nine local unit tests cover explicit slide order, PDF page ratio/count, one-picture PPTX structure, incorrect ratios, native rounding disclosure, unreviewed draft behavior, overwrite refusal, duplicate/missing paths and IDs, path escape, Boolean review flags, and required exact-copy records. These are mechanics tests, not taste/spelling/scientific-validity tests.

## Runnable UI example

In the in-app browser, the local prototype was exercised for empty dates, reversed dates, a valid local request/loading-to-success state, unavailable-item recovery, and reset. Error focus and visible status feedback were observed. Desktop output was inspected visually. A 390-pixel viewport check showed stacked sections, contained fields and no horizontal document overflow; the full narrow screenshot was inspected.

No real owner, account, message, payment or database integration exists. Physical-device gestures, independent screen-reader testing and comprehensive accessibility certification were not performed.

## Video example

The original renderer produced a labeled 12-second silent motion study at 1280×720 and 30 fps, plus GIF/frame preview. FFmpeg metadata confirms those properties and no audio stream. A representative frame was inspected. This demonstrates simple meaningful motion only; it is not the requested production pattern's complete narrated film.

No voice generation/audition/listening comparison was performed. Voice instructions require a real listening gate and honest unrun status when direct listening is unavailable. Script/storyboard timing remains a planning example.

## Independent agent passes

- A fresh agent performed a local text-only GPT handoff from the fictional source and skill instructions. It produced a resolved brief, ten-entry source ledger, three standalone prompts, exact-copy record, draft manifest with unreviewed entries and pending QA. It did not generate media, call an API, install software, publish, or read evaluation expectations. No blockers were reported.
- Its clarity findings were incorporated: handoff completion appears in the entry point, handoff has separate acceptance criteria, and significant versus ordinary display spacing is defined.
- A separate agent reviewed portability/publication contents and ran the existing mechanics tests. Findings about final validation documentation, packaging-report wording and required copy records were addressed. Repository-root verification is required before staging, so an ancestor checkout cannot include unrelated files.

The agents are independent sessions, not an independent human panel or a cross-model reliability benchmark. Future evaluations can use [the behavior cases](evaluations/README.md) and actual artifacts to refine the library.

## Research, domain and UI-choice expansion

The complete supplied narrative report is archived with a historical/overriding-contract note and one disclosed local-link adaptation. The original 58-row CSV remains byte-for-byte unchanged. The coverage JSON maps every source to existing integration files and separates rule/workflow references from optional engines, creator practice and discovery-only material.

Eleven domain packs and fifteen local editable production templates are indexed as 165 possible compositions. The validator checks the domain/skill sets, file paths, composition count and all-source mapping. This is coverage of reusable instructions, not 165 executed or certified creative workflows. An independent read-only agent verified the report/CSV incorporation, mapped files, domains/templates and absence of private reference assets; its optional-domain wording finding was addressed so installed skills do not require the full repo.

The UI choice policy is an explicit user preference. The original chooser supplies three structurally distinct same-content care-portal specimens. Root inspected the desktop render and exercised selection, exclusive state, URL-fragment restoration after reload, switching direction and clear/reset with focus recovery. A 390-pixel DOM check showed three options/controls and no horizontal overflow. The narrow full-page screenshot could not be captured, so narrow visual inspection and real screen-reader checks are not claimed.

The accepted Morrow Care patient portal is included as a runnable fictional example. Root inspected desktop rendering, missing-day/time booking recovery, valid local booking/loading/confirmation, updated appointment list and reset. No real provider was contacted. Other available actions are implementation examples; their exhaustive browser/device validation is not claimed. All source remains administrative/fictional rather than clinical guidance.
