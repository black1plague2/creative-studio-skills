# SaaS: tell the product truth through its task

Use for software product pitches, onboarding, dashboards, operational interfaces and product websites. Distinguish implemented capability from proposed flow and demo-only state. Use a task-specific visual vocabulary rather than invented enterprise logos and dashboard numbers.

## Editable brief

- User role, permission level and primary job: [fill].
- Trigger → task → outcome: [fill].
- Implemented versus proposed feature list: [fill].
- Real screenshot/data source and reference role: [fill].
- Integration, performance and customer claims with evidence: [fill].
- Output environment and existing design system/stack: [fill].

Ask: Which role performs the main task, and what access do they have? Which features actually work today? What real evidence can support productivity, integrations or customer claims? Choose reversible tokens/compositions without asking the user to design every component.

## Creative constraints

Public marketing and authenticated work surfaces have different jobs. Show credible empty/error/loading states and meaningful recovery. Do not invent charts, activity feeds, integrations, testimonials or compliance/security badges. A generated screenshot is a concept illustration, not proof of implemented UI. Keep permission and destructive-action behavior faithful to the source.

## Filled fictional exercise — QueueDesk

Original fictional prototype for a two-person support team. Role: support coordinator. Proposed task: review an unassigned ticket → select an owner → save assignment. Sample tickets have synthetic subjects and no customer data. A failed save retains the selected owner and offers retry. There is no automated triage, external integration or measured response-time improvement. Exact draft headline: **“Give each request a clear owner.”** UI action: **“Assign owner.”** Error: **“Assignment wasn’t saved. Your selection is kept. Try again.”**

## Task adaptations

| Group | Domain-specific treatment |
|---|---|
| Brief and language | Keep product status visible and describe assigned ownership, not unsupported efficiency percentages. |
| Slide and poster | Complete GPT 16:9 posters illustrate coordinator, request and owner relationship; architecture appears only where the source actually requires it. |
| Reading documents | Proposal separates user need, scope, flow, states and open integration decisions; preserve implementation limits beside benefit descriptions. |
| Website and app | Marketing CTA is “Explore the prototype”; task UI tests selection, focus, saving, failure retention and retry. Role restrictions remain explicit. |
| Video, voice and interaction | Show the owner changing at the narrated anchor, then a recovery example if useful. Listen for a colleague explaining a task rather than promotional sing-song. Interactive demo permits selection and shows a simulated save. |
| Identity, assets and campaign | Tight role-based tokens for product, expressive editorial framing for campaign; maintain vocabulary and object continuity without imposing marketing density on a dashboard. |
| Data and evidence | Synthetic ticket counts must be labeled demo data; no real performance claim follows from them. Real throughput comparisons need period, team size and denominator. |

Review failure example: UI flashes “Saved” before a failed request and discards selection. Repair state/meaning first, then update any video or poster depicting that outcome.
