# Give the user concrete UI examples to choose from

This is an explicit user preference for this repository. For a newly requested UI artifact or visual redesign—website, app, dashboard, portal, mobile screen, mockup or component—**offer three concrete examples/directions before settling the final UI**. The goal is a real choice, not an abstract question about “modern versus clean.”

## What to show

Use the same real task/content in each option so the user can compare what changes. Show an actual rendered specimen when tools permit: representative screen, hero/content region, component with relevant states, or a small working HTML preview. Keep option labels and explanation outside the specimen. Name the practical differences in typography, layout, density, imagery and interaction—not just a color swap.

The [three-option gallery](../examples/ui-directions/README.md) is an original reusable demonstration. Its care-portal content is fictional. For another domain, adapt the examples to that product's audience, content and constraints; do not turn every requested UI into a healthtech template.

## Selection and scope

Ask a concise preference question after the examples are concrete. If the user already chose a direction, retain it for follow-ups. If they provided a precise brand/reference, preserve those constraints and show compatible variations rather than proposing an unrelated redesign. If they explicitly opt out of options or say to choose for them, honor that instruction and proceed; do not manufacture an approval ritual.

Once selected, save the chosen direction in the working brief and build the complete interaction states within that identity. Do not ask again for fonts/colors/spacing already determined. A review, bug fix, or small follow-up should preserve the accepted design; do not broaden it into an unrelated redesign just to show three templates.

## Capability honesty

Use the rendering/generation/browser tools actually available. If a host cannot render, provide clearly labeled HTML/SVG specimens or source-linked references that the user can view, and explain the limitation. Do not describe a prose list or an ungenerated image prompt as a rendered UI example. Missing rendering is not permission to invent screenshots.

## Reusable choice record

| Option | Real content represented | Type/layout/density/imagery difference | Task/brand fit | Render/reference evidence |
|---|---|---|---|---|
| A | Main task and a useful state | Coherent direction | Why it works here | Actual preview or truthful handoff |
| B | Same task/content | Materially different treatment | Tradeoff | Actual preview or truthful handoff |
| C | Same task/content | Materially different treatment | Tradeoff | Actual preview or truthful handoff |

Record selected option, any mix requested, preserved constraints and rationale. A choice preview is an art-direction sample; it is not proof that the whole app, backend, accessibility or production integration is complete.
